# Drafting replies

Every reply is public, permanent, and mailed to the reviewers. Two shapes, chosen by who wrote the
comment: `/aino` for the bot, plain prose for a person.

## `/aino` — telling the bot it is wrong

`/aino` states that the finding does not apply. It is a public claim that the bot misread the code,
so the bar is evidence, not an opinion.

Shape: `/aino ` plus one or two sentences naming the code that disproves the claim.

```text
Good  /aino The guard on line 41 returns early when `cfg` is null, so line 44 cannot deref null.
Good  /aino src/gen/api.ts is generated by `pnpm codegen` and is listed in .prettierignore.
Bad   /aino False positive.
Bad   /aino Not relevant to this change.
```

Use `/aino` only for state **wrong**: a misread of the code, a rule that does not cover this file
type, or a hit inside generated or vendored code.

Never use `/aino` for:

- A **stale** finding. The code did change, so the new patchset answers it. A dismissal there is a
  false claim.
- A **blocked** finding. The bot is right and the fix is expensive. That needs the owner.
- Any security or secret finding. Escalate to the owner instead.
- A finding you could not ground in Phase 3. No evidence means no dismissal.
- Anything a person wrote. `/aino` is a bot command; aimed at a colleague it reads as a brush-off,
  and it does nothing to the vote that is holding the change.

## Replying to a person

The reviewer decides whether their comment is answered, so the reply's job is to give them what they
need to decide in one read: what you did, or why the code already does it. Then stop.

Shape: one or two sentences. Lead with the outcome, then the evidence.

**Fixed.** Say what changed, so they can review the fix rather than re-derive it.

```text
Good  Done in patchset 4 — extracted `parseWindow`, and both call sites now share it.
Bad   Done.
```

`Done.` is true and still costs them a four-file diff to find out what it means.

**Already handled.** A reviewer looking at patchset 2 has no way to know patchset 3 fixed it.

```text
Good  Fixed in patchset 3, before this thread — the retry now backs off from `initialDelay`.
```

**You think they misread.** Show the code and hand the decision back. You are not the arbiter of
your own change.

```text
Good  The `ok` check on line 38 already covers that path, so the deref on 44 is guarded — unless
      you mean the async branch below, which I think does need it. Happy to add the check there
      if you'd rather be explicit.
Bad   That's incorrect, see line 38.
Bad   Won't fix.
```

The first bad one is factually right and still worse: it closes a conversation the reviewer has not
finished. The second offers no evidence and no way forward.

**Too expensive for this change.** Name the cost and offer the follow-up, so the answer is a plan
rather than a refusal.

```text
Good  Agreed, but the signature is public and three callers live outside this repo. I'd rather do
      it as a follow-up — want me to file it?
```

**A question.** Answer it and add nothing else. No code change, no defence.

```text
Good  The lock is on the map rather than the entry because two goroutines can insert the same key,
      and per-entry locking would still need the map guarded.
```

## Rules that hold for every reply

- Answer the comment that was written, not the one that was easiest to answer.
- Cite code by file and line, or by the patchset that changed it. An assertion with no reference
  makes the reviewer do the work twice.
- Name a change by its number or its `Change-Id`, never by a commit sha. A rebase or a cherry-pick
  gives the change a new sha and keeps the `Change-Id`, so a sha in a reply stops resolving. Use a
  patchset number when you do mean one specific revision — that is the only case a revision belongs
  in the text at all.
- Never say a fix landed before the push actually lands it. Phase 8 runs after Phase 7 for this
  reason.
- Do not thank, apologise, or narrate your reasoning. The reviewer wants the state of the code.
- Disagreement gets one round from you. If they press again, that goes to the owner.
- A suppression is a partial answer at best, so say which it was. A reply that reads as a fix when
  it was an `eslint-disable` costs the next reviewer their time.

```text
Good  Silenced with `// nolint` on 88 — the analyzer can't see that `id` is validated in
      `parseRequest`. Happy to restructure instead if you'd prefer the check be visible here.
```
